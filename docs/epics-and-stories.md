# MVP

- Epic: Task Due Date
  - Story: Add due date field to task
    - Acceptance Criteria:
      - A due date input is available when creating and editing a task.
      - The input accepts ISO format `YYYY-MM-DD`.
      - The due date is optional; tasks can be saved without a due date.
      - When present and valid, the due date is persisted in local storage with the task.
    - Technical Requirements:
      - Frontend uses a date input bound to the task `due_date` string (see MUI `TextField` of type `date`).
      - Normalize incoming `due_date` to `YYYY-MM-DD` (e.g., helper similar to `normalizeDateString`).
      - Backend POST/PUT should accept `due_date` as `YYYY-MM-DD` or `null` and store as DATE when API mode is used.
      - In local storage mode, persist `due_date` string as-is under the tasks array.
  - Story: Validate ISO YYYY-MM-DD input
    - Acceptance Criteria:
      - Non-ISO or invalid dates (e.g., `2025-13-40`) are treated as invalid.
      - Invalid due dates do not block saving the task; they are ignored (treated as absent).
      - The app remains stable when invalid input is entered (no crashes).
    - Technical Requirements:
      - Frontend validation: accept only `/^\d{4}-\d{2}-\d{2}$/`; otherwise set `due_date` to empty before submit.
      - Do not attempt to coerce invalid dates; skip sending `due_date` in API/local storage payload when invalid.
      - Ensure edit mode rehydrates `due_date` in `YYYY-MM-DD` format for the date input.
  - Story: Ignore invalid due dates
    - Acceptance Criteria:
      - If an invalid date is entered, no `dueDate` value is stored for the task.
      - Tasks with invalid/absent `dueDate` are excluded from Today and Overdue filters.
      - Other task fields are saved as expected.
    - Technical Requirements:
      - Submission logic conditionally omits `due_date` when invalid; backend receives `null` or field omitted; local storage stores no `due_date` key.
      - Filtering utilities treat falsy/empty `due_date` as undated and exclude from date-based views.

- Epic: Task Priority
  - Story: Add priority enum P1|P2|P3
    - Acceptance Criteria:
      - The priority field presents options `P1`, `P2`, `P3` only.
      - Selected priority is persisted with the task in local storage.
      - Creating and editing tasks allows changing the priority.
    - Technical Requirements:
      - Frontend: add priority select bound to `priority` string on the task model.
      - Backend: extend schema with `priority TEXT CHECK(priority IN ('P1','P2','P3')) DEFAULT 'P3'` and include `priority` in POST/PUT responses when API mode is used.
      - Local storage provider includes `priority` in the stored task object and defaults to `P3` when absent.
  - Story: Set default priority to P3
    - Acceptance Criteria:
      - If the user does not select a priority, the task is saved with `P3`.
      - Existing tasks without an explicit priority load/display as `P3`.
    - Technical Requirements:
      - Frontend defaults `priority` state to `P3` on create.
      - Backend layer applies default `P3` when `priority` is missing; local storage initializer sets `priority: 'P3'`.
  - Story: Display priority in task list
    - Acceptance Criteria:
      - Each task shows its priority label (`P1`, `P2`, or `P3`) in the list view.
      - Display does not require color-coding in MVP; text label is sufficient.
    - Technical Requirements:
      - Task list component renders a compact label next to the title or in the actions area.
      - Ensure rendering covers both API-provided tasks (with `priority`) and local storage tasks.

- Epic: Filtering Views
  - Story: Implement All view
    - Acceptance Criteria:
      - All tasks are visible, including completed and incomplete.
      - Tasks with and without due dates appear in this view.
    - Technical Requirements:
      - Frontend fetches tasks once and applies view filters client-side.
      - If backend query params are used, avoid `completed` filtering for All (or fetch without query and display all).
  - Story: Implement Today view for incomplete tasks
    - Acceptance Criteria:
      - Shows tasks with a valid `dueDate` equal to the current calendar date.
      - Includes only incomplete tasks; completed tasks are excluded.
      - Tasks without a valid `dueDate` do not appear.
    - Technical Requirements:
      - Frontend computes today as local calendar date; compare `due_date` strings (YYYY-MM-DD) to today.
      - Apply completion filter client-side (`completed` falsy/0/false); optionally use backend `completed=false` param.
  - Story: Implement Overdue view for incomplete tasks
    - Acceptance Criteria:
      - Shows tasks with a valid `dueDate` earlier than today.
      - Includes only incomplete tasks; completed tasks are excluded.
      - Tasks without a valid `dueDate` do not appear.
    - Technical Requirements:
      - Frontend determines overdue by `due_date < today` using string comparison on `YYYY-MM-DD` or date objects.
      - Apply completion filter client-side; optionally leverage backend `completed=false`.

- Epic: Local Persistence
  - Story: Persist tasks in local storage
    - Acceptance Criteria:
      - Creating, editing, completing, and deleting tasks updates data stored in browser local storage.
      - Persisted fields include: `title`, `priority`, `dueDate` (when valid), and completion status.
      - Persistence operations succeed without requiring a backend.
    - Technical Requirements:
      - Introduce a data provider abstraction with two adapters: `LocalStorageProvider` and `ApiProvider`.
      - `LocalStorageProvider` reads/writes to `window.localStorage` under a stable key (e.g., `todo.tasks`) with JSON array schema.
      - Implement CRUD: create (assign incremental `id`), update, patch completion, delete, and list.
      - Gate provider selection via configuration (e.g., env flag) to allow running without backend.
  - Story: Load tasks from local storage on startup
    - Acceptance Criteria:
      - On app load, tasks are read from local storage and rendered.
      - If no tasks are stored, the app initializes with an empty list without errors.
    - Technical Requirements:
      - Read and parse JSON from local storage at boot; handle missing/invalid payloads gracefully by falling back to `[]`.
      - Ensure UI state hydrates from provider response before rendering lists.

- Epic: Basic Validation
  - Story: Require title on task creation
    - Acceptance Criteria:
      - A task cannot be saved without a non-empty `title`.
      - When `title` is present, it is persisted and displayed in lists and details.
    - Technical Requirements:
      - Frontend validates `title.trim().length > 0` and surfaces error inline; disable submit when invalid.
      - Backend already enforces `title` required in POST/PUT; local storage provider mirrors this check and rejects invalid saves.

# Post-MVP

- Epic: Overdue Highlighting
  - Story: Visually highlight overdue tasks in list
    - Acceptance Criteria:
      - Incomplete tasks with `dueDate` earlier than today are visually distinguished (e.g., red treatment) from other tasks.
      - Highlighting applies consistently across views that display overdue tasks.
    - Technical Requirements:
      - Add UI logic to detect overdue in list rendering; apply MUI styling (e.g., red border/background consistent with UI guidelines).
      - Compute overdue on client using local date to avoid timezone issues; ensure accessibility contrast.

- Epic: Task Sorting
  - Story: Sort overdue tasks first
    - Acceptance Criteria:
      - Task lists order overdue incomplete tasks before all other tasks.
    - Technical Requirements:
      - Implement a client-side comparator that groups overdue incomplete tasks at the top regardless of other attributes.
      - Alternatively, extend backend `GET /api/tasks` with ORDER BY logic using `due_date < date('now')` and `completed = 0` when API mode is used.
  - Story: Sort by priority P1→P3
    - Acceptance Criteria:
      - Within the same overdue/non-overdue grouping, tasks are ordered by priority: `P1` before `P2` before `P3`.
    - Technical Requirements:
      - Require `priority` field on tasks; include in sort comparator mapping `P1=1, P2=2, P3=3`.
      - Backend sort path requires adding `priority` column and including it in ORDER BY if server-side sorting is chosen.
  - Story: Sort by due date ascending
    - Acceptance Criteria:
      - Within the same priority, tasks with earlier `dueDate` appear before later `dueDate`.
    - Technical Requirements:
      - Compare `YYYY-MM-DD` strings or Date objects consistently; ensure stable sort.
      - Backend mode: ensure DATE column ordering is ascending and consistent with client expectations.
  - Story: Place undated tasks last
    - Acceptance Criteria:
      - Tasks without a `dueDate` appear after all tasks with a valid `dueDate`.
      - Ordering of undated tasks among themselves is unspecified in PRD and may default to creation/display order.
    - Technical Requirements:
      - Client-side comparator places null/empty `due_date` at the end.
      - Backend ORDER BY should include `due_date IS NULL` first term if server-side sorting path is used.
